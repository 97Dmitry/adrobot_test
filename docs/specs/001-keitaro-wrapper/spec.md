# Обёртка над Keitaro

Статус: согласована пользователем 2026-11-17; реализация разрешена.
Дата: 2026-11-17.

## Назначение и границы

Выполнить тестовое Adrobot: создавать кампании с двумя потоками и редактировать
наборы офферов существующих потоков, воспроизводя состояния из видео.
Результат — приложение FastAPI + SQLAlchemy с интерфейсом, миграциями Alembic,
проверками и README для запуска из чистого checkout.

Источник требований — ТЗ, изображения и транскрипция в задании пользователя.
Изменения кампаний через Admin API разрешены пользователем. Все кампании,
создаваемые приложением и проверками, имеют префикс `test_tsybizov_`.
Пользователь отдельно разрешил создание GitHub-репозитория, ветки, коммиты,
push, PR и слияния завершённых этапов в main 2026-11-17.

Не входят: отчёты о кликах и доходах, собственный трекер редиректов, загрузка
лендингов, управление содержимым офферов, фоновая синхронизация и несколько
пользователей с ролями. Приложение рассчитано на локальную работу одного оператора.

## Подтверждённые условия интеграции

- Admin API: `https://tlgk.host/admin_api/v1/`; ключ передаётся сервером в `Api-Key`.
- Проверка чтения выполнена 2026-11-17: доступны domains, groups, traffic_sources,
  offers, campaigns, stream_filters и streams_actions.
- Доступный домен: `kylovoa.com`, ID 1813; источник `FORTESTS`, ID 836.
  Значения не вшиваются в код: форма получает актуальные справочники API.
- Сервер принимает именованный `User-Agent: Adrobot-Test/1.0`; стандартный
  User-Agent Python получил Cloudflare 403. Клиент задаёт своё имя явно.
- Официальный контракт: <https://admin-api.docs.keitaro.io/openapi.json>.
  Описание частичного PUT: <https://docs.keitaro.io/en/development/admin-api.html>.
- Чтение API подтверждает доступ, но не подтверждает payload создания потоков:
  его нужно проверить интеграционным сценарием на собственной тестовой кампании.

Секреты находятся только в окружении или исключённом из Git `.env`. Они не
передаются браузеру, не включаются в тестовые фикстуры, документацию или логи.

## Подходы и рекомендация

1. **FastAPI + SQLAlchemy + Alembic, HTML/CSS/JavaScript с того же сервера** —
   рекомендуемый подход. Один процесс, одна точка запуска, без Node-сборки;
   состояния и расчёты проверяются в Python. SQLite достаточна для одного оператора.
2. **FastAPI + отдельный React-клиент** — уместен для более сложного интерфейса,
   но добавляет сборку и второй набор зависимостей без необходимости по ТЗ.
3. **Тонкий прокси без локальной БД** — не подходит: не сохраняет архив удалённых
   привязок, черновики и закрепления весов между перезапусками.

Выбор первого подхода — рекомендация исполнителя. Детали интерфейса оставлены
исполнителю исходным ТЗ. Redis, очереди и дополнительные сервисы не требуются.

## Пользовательские сценарии и критерии приёмки

### US1. Создание кампании

- **AC1.1** Форма принимает имя, один или несколько ISO 3166-1 alpha-2 кодов
  стран, один существующий ID оффера, домен, группу кампаний и источник.
  Несколько стран поддерживаются по примеру `MX,AU,RO`; минимум — одна.
- **AC1.2** Предлагается префикс `test_tsybizov_`; сервер добавляет его, если
  пользователь ввёл только суффикс. Пустой суффикс запрещён. Alias уникален.
- **AC1.3** В Keitaro создаётся кампания с ротацией `position`, выбранными
  доменом, группой и источником. Перед созданием проверяется существование
  выбранного оффера и справочников.
- **AC1.4** Первый поток принимает посетителей из заданных стран и выполняет
  HTTP-редирект на `https://google.com/`. Второй, расположенный после него,
  принимает остальных и содержит выбранный оффер с весом 100%.
- **AC1.5** Пользователь получает ID кампании и трекинговую ссылку. Созданная
  кампания сразу доступна редактору.
- **AC1.6** Ошибка любого шага не показывается как успех. Кампания создаётся
  выключенной и включается только после успешной настройки обоих потоков.
  При частичном сбое до включения показывается ID выключенной кампании для
  проверки; автоматического удаления и повторного POST нет. Если ответ на
  включение потерян, состояние проверяется чтением; при недоступности чтения
  показывается «состояние неизвестно, требуется сверка», без обещания отключения.
- **AC1.7** Повторная отправка одного запроса создания с тем же ключом операции
  не создаёт вторую кампанию; при неизвестном исходе POST требуется сверка.

### US2. Загрузка и синхронизация

- **AC2.1** Можно выбрать существующую кампанию или загрузить её по ID.
  Список кампаний поддерживает поиск; отсутствие результатов видно явно.
- **AC2.2** Загрузка потоков — явное действие. Интерфейс показывает каждый
  поток и его название. Поток без офферов показывается без попытки распарсить
  фильтры и редиректы; его содержимое не меняется. Исключение: если ранее
  импортированный поток имеет совместимую схему `landings` и локальный архив,
  архив показывается и Bring back доступен даже при пустом удалённом наборе.
  Поток со схемой редиректа/действия редактор не преобразует в офферный.
- **AC2.3** У офферов видны ID, название, текущий вес, закрепление и состояние.
  Данные после перезагрузки страницы восстанавливаются из локальной БД,
  включая неопубликованные изменения.
- **AC2.4** При следующей синхронизации исчезнувшая из Keitaro известная
  привязка становится архивной с 0%, а не удаляется из локальной истории.
  Новые привязки импортируются, веса берутся из Keitaro без самовольного расчёта.
- **AC2.5** Синхронизация при наличии черновиков блокируется с понятным сообщением:
  сначала Publish или Cancel. Черновики молча не теряются.
- **AC2.6** Если поток удалён в Keitaro, интерфейс отмечает его недоступным
  и запрещает публикацию. Архив его привязок сохраняется локально.

### US3. Изменения и публикация

- **AC3.1** Поиск оффера по ID или фрагменту названия вызывает API обёртки,
  который получает данные Keitaro; поиск имеет задержку ввода и ограничение выдачи.
  Неизвестный или удалённый оффер добавить нельзя. Дубликаты запрещены.
- **AC3.2** Add, Remove, Bring back и изменение закрепления создают локальный
  черновик и выделяют поток жёлтым. До Publish в Keitaro нет записи.
- **AC3.3** Remove делает привязку серой с весом 0%. После Publish она исчезает
  из массива офферов Keitaro, но остаётся в локальном архиве с Bring back.
- **AC3.4** Bring back возвращает архивную привязку в черновик; публикация
  возвращает её в Keitaro. Существующий архив не дублируется.
- **AC3.5** Cancel восстанавливает опубликованные привязки и закрепления.
  Новые неопубликованные привязки удаляются; карточка самого оффера остаётся.
  Ранее опубликованный архив сохраняется. Поток теряет жёлтое выделение.
- **AC3.6** Publish работает отдельно для потока и передаёт только массив
  офферов, не перезаписывая фильтры, landings, редирект, позицию или прочие поля.
  Пустой набор активных офферов публиковать нельзя; можно отменить черновик.
- **AC3.7** Перед Publish повторно читается поток. Если его набор офферов,
  состояния/веса привязок либо схема изменились после загрузки, операция
  возвращает конфликт, сохраняет черновик и не перезаписывает Keitaro.
- **AC3.8** API-ошибка сохраняет черновик и показывает доступную пользователю
  причину. Таймаут записи означает неизвестный результат, а не гарантированный
  откат: перед повтором выполняется чтение и сверка ожидаемого результата.
- **AC3.9** Повторное нажатие кнопки или запрос из устаревшей вкладки не
  перезаписывает более свежий локальный черновик: операции используют ревизию.

### US4. Веса и закрепления

- **AC4.1** Веса — целые проценты; после любой операции перерасчёта сумма
  активных офферов равна ровно 100%. Архивные привязки всегда имеют 0%.
- **AC4.2** Без закреплений распределение максимально равномерное:
  три оффера получают 34/33/33, четыре — 25/25/25/25.
  Остаток по 1% получают первые офферы в стабильном порядке привязок.
- **AC4.3** Закреплённые активные веса не меняются при Add/Remove/Bring back.
  Остальные поровну делят `100 - сумма закреплений` с тем же правилом остатка.
  Например: 25% закреплено, два остальных получают 38% и 37%.
- **AC4.4** Закрепление принимает целое значение 1..100. Если сумма превышает
  100%, либо остатка недостаточно хотя бы для 1% на каждый незакреплённый
  активный оффер, операция отвергается целиком с сообщением.
- **AC4.5** Если все активные офферы закреплены, их сумма обязана быть 100%.
  Remove последнего оффера допускается как черновик, но блокирует Publish.
- **AC4.6** Закрепление — локальное свойство, Keitaro получает только вес.
  Архивное закрепление помнится, но не участвует в сумме; Bring back валидирует
  его заново. Cancel восстанавливает опубликованное состояние закреплений.
- **AC4.7** При синхронизации внешние веса имеют приоритет. Если вес
  закреплённой привязки изменён извне, закрепление снимается с уведомлением;
  неизменённые закрепления сохраняются. Импорт сам не пересчитывает веса.

## Данные и согласованность

- `Campaign` — удалённый ID, имя, ссылка, состояние создания, ключ операции.
- `Stream` — удалённый ID, кампания, имя, опубликованный снимок редактируемых
  полей, локальная ревизия, признак черновика и состояние удалённой записи.
- `Offer` — удалённый ID и название, загружаемые из Keitaro.
- `StreamOffer` — уникальная пара поток/оффер, стабильный порядок, опубликованные
  и черновые active/share/pin, признак когда-либо опубликованной привязки.

Редактируемые поля снимка нужны для проверки внешних изменений; фильтры и
содержимое потоков без офферов не интерпретируются. Глобальный кэш офферов
не является источником истины о наличии привязки в потоке.

SQL-транзакция не охватывает Keitaro. Перед удалённой записью сохраняются её
намерение и ожидаемые офферы; после ответа выполняются чтение и сверка.
При сбое между PUT и локальным commit следующий Publish сначала сверяет
удалённое состояние: совпадение завершает локальное сохранение, несовпадение
даёт конфликт. Автоматические повторы мутирующих запросов запрещены.

Операции над одним потоком сериализуются в пределах одного процесса;
ревизии защищают от устаревших вкладок. Приложение запускается одним worker.
Внешняя гонка между проверкой и PUT остаётся ограничением Admin API без
условной записи; README должен прямо это объяснять, а не обещать атомарность.

## Интерфейс

Одна страница: форма создания, выбор/загрузка существующей кампании, карточки
потоков и таблицы офферов. Действия потока: загрузка данных, Publish, Cancel;
действия строки: Remove/Bring back, ввод веса и Pin. Для потока без офферов —
название и пояснение отсутствия офферов; при наличии локального архива и
совместимой схемы также доступны архивные строки и восстановление.
Состояния ошибок и загрузки видимы;
одних цветов недостаточно, есть текстовые статусы. Кнопки защищены от
двойного нажатия, список поиска доступен с клавиатуры.

## Проверки и сдача

- **VT1 → US1:** интеграционный сценарий клиента проверяет payload создания,
  порядок потоков, фильтр country/accept, настройки и частичные сбои.
- **VT2 → US2/US3:** тесты импорта, внешнего удаления, архива, Cancel,
  Restore, сохранения после нового запроса/сеанса и конфликта публикации.
- **VT3 → US4:** тесты округления, стабильности, закреплений, границ и ошибок.
  Проверка инвариантов на наборах операций, а не только отдельных примеров.
- **VT4 → US3:** сбой ответа после успешного PUT, повторная публикация,
  неизвестный исход, устаревшая ревизия и отсутствие изменений чужих полей.
- **VT5:** миграции на пустой временной SQLite, upgrade/downgrade/upgrade,
  запуск приложения и HTTP-проверка интерфейса.
- **VT6:** ручная/браузерная проверка всех кнопок и поиска; результат и
  ограничения фиксируются честно, без подмены браузерной проверки unit-тестами.
- **VT7:** реальный smoke через приложение на кампании `test_tsybizov_*`:
  создание, чтение двух потоков, Add/Cancel, Add/Publish, Remove/Publish,
  Bring back/Publish, закрепление. Внешнее удаление проверяется только на
  собственной кампании через ограниченный проверочный сценарий.

Проверки не запускают переходы по трекинговым ссылкам: это создаёт клики и
может исполнить содержимое офферов. Настройка маршрутизации проверяется API;
фактическая геомаршрутизация требует контролируемых IP и отмечается отдельно.

README содержит требования, настройку `.env`, установку с зафиксированными
зависимостями, миграции и запуск, тесты, сценарий демонстрации и ограничения.
Перед внешней публикацией проверяется отсутствие секретов и локальной БД.

## Процесс SDD

1. Согласовать эту спецификацию, закрыв важные вопросы до реализации.
2. Создать `plan.md`: модули, API обёртки, таблицы, миграции и обработка ошибок.
3. Создать `tasks.md` с небольшими проверяемыми задачами и ссылками на AC/VT.
4. Реализовывать задачи, начиная с проверок доменной логики и API-контрактов.
5. Сверить результат с каждым критерием и записать свидетельства в `verification.md`.

Документы обновляются по фактическим решениям; непройденная проверка не
отмечается выполненной. Не добавлять инфраструктуру ради демонстрации SDD.

Независимая проверка спецификации выявила два случая, уточнённых до реализации:
неизвестный исход включения кампании и восстановление полностью очищенного
извне потока. Эти решения приняты исполнителем как следствие обработки
распределённых сбоев и требования сохранять архив; это не новые пожелания пользователя.
